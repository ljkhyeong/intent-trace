# IntentTrace 0.12.0 이후 개선 검토

검토일: 2026-09-05

기준 커밋: `4205cf78ebe85db1bac70ebbf4393b81b21b5f62`

검토 당시 상태: 설치·조회 중 오류 처리 보완 제안.

후속 처리: 세 항목을 0.12.1에 반영했다. 구현 결과와 실행한 검증은 [0.12.1 검증 기록](2026-09-05-v0.12.1-verification.md)을 따른다. 아래 재현 결과는 수정 전 코드 기준이다.

0.12.0에 추가한 설치·조회 기능에서 오류를 제대로 처리하는지 확인했다. 이번에는 세 가지 보완을 우선한다. 새 제품 기능의 확대는 실제 사용 결과를 확인한 뒤 결정할 수 있다.

## 우선순위

| 순서 | 우선순위 | 항목 | 확인 방법 |
|---|---|---|---|
| 1 | P1 | 숨긴 토큰 입력을 보장할 수 없을 때 실행 중단 | 제어 터미널이 없는 자식 프로세스에서 경고 후 실행 지속 재현 |
| 2 | P2 | 배포 파일의 의존성을 잠금 파일과 일치시킴 | 임시 프로젝트에서 선언·잠금 1.0.0, 설치 2.0.0을 묶는 현상 재현 |
| 3 | P2 | 진행할 수 없는 조회 제한과 재개 안내 | 호출 제한 1회를 허용하는 정책과 매 요청의 캐시 초기화·근거 재개 위치를 코드로 확인 |

## 1. 숨긴 토큰 입력 실패 처리

[Zed 실행 도구](../../scripts/zed-with-intent-trace.py)는 환경 변수에 세션이 없으면 `getpass.getpass`를 호출한다. `GetPassWarning`은 처리하지 않는다. Python은 숨긴 입력을 제공할 수 없을 때 경고 후 표준 입력을 읽을 수 있다. [Python 공식 문서](https://docs.python.org/3/library/getpass.html)

실제 사용자 세션을 사용하지 않고, 제어 터미널이 없는 새 프로세스에 합성 `its_` 값과 임시 Zed 대역을 제공했다.

| 관찰 | 결과 |
|---|---|
| 입력 표시를 제어할 수 없다는 경고 | 발생 |
| 입력이 표시될 수 있다는 경고 | 발생 |
| Zed 대역 실행 | 실행됨 |
| 종료 코드 | 0 |

이 재현은 입력 보호 실패를 감지하고도 실행을 계속한다는 것을 확인했다. 파이프로 제공한 합성 token이 실제 화면에 표시됐다는 검증은 아니다. 현재 안내의 숨긴 입력 보장을 유지하려면 이 경고를 실패로 처리해야 한다.

완료 기준:

- 숨긴 입력을 제공할 수 없으면 입력 대체 경로를 진행하기 전에 중단하고, 지원되는 터미널 또는 이미 주입한 환경 변수를 사용하도록 안내한다.
- 사용자가 미리 환경 변수로 제공한 세션을 사용하는 비대화형 실행은 유지한다.
- 입력 취소·입력 종료를 짧은 한국어 안내와 실패 종료 코드로 처리한다. token과 traceback을 출력하지 않는다.
- 필요한 검증은 숨긴 입력 실패 시 Zed 미실행, 환경 변수 입력의 기존 실행, 입력 취소에 한정한다.

## 2. 잠금 파일과 일치하는 배포 의존성

[패키지 생성기](../../scripts/package-zed.mjs)는 작업 폴더의 `node_modules`를 임시 폴더에 복사한다. 생성기 안에서는 `package-lock.json`을 읽거나 설치된 의존성과 대조하지 않는다. 따라서 잠금 파일을 갱신한 뒤 의존성을 다시 설치하지 않았거나 다른 작업에서 설치 폴더가 바뀐 경우에도 패키지를 만들 수 있다.

실제 저장소의 의존성을 건드리지 않고 생성기 사본과 작은 임시 프로젝트를 사용했다.

| 항목 | 값 |
|---|---|
| `package.json`의 의존성 | 1.0.0 |
| `package-lock.json`의 의존성 | 1.0.0 |
| `node_modules`의 설치 버전 | 2.0.0 |
| 생성한 `.tgz` 안의 버전 | 2.0.0 |
| 생성 명령 종료 코드 | 0 |

0.12.0 검증에서는 `npm ci` 후 패키지를 생성했다. 이번 결과는 임시 환경의 불일치 재현이며 앞서 생성한 0.12.0 파일의 의존성 오류를 확인한 것은 아니다. 현재 SHA-256 파일은 생성된 압축 파일이 바뀌었는지를 확인하지만, 어떤 의존성이 포함되어야 하는지는 확인하지 않는다.

완료 기준:

- 잠금 파일에서 임시 설치 폴더를 구성하거나, 잠금 파일과 다른 설치 상태의 패키지 생성을 거부한다. 직접 의존성과 하위 의존성 모두 같은 기준을 적용한다.
- 의존성 준비에서 설치 스크립트를 실행하지 않고 기존 작업 폴더를 변경하지 않는다.
- 정상 설치·오프라인 소비자 설치 검증을 유지하고, 의존성이 다른 배포 입력을 처리하는 최소 검증을 추가한다.
- 배포 패키지의 버전과 잠금 파일 기준을 기록해 같은 버전의 산출물 내용을 확인할 수 있게 한다. 계정 인증 정보와 개인 설치 경로는 포함하지 않는다.

## 3. 진행할 수 없는 조회 제한과 재개 안내

[조회 제한 정책](../../src/main/kotlin/io/intenttrace/record/application/EvidenceReadBudget.kt)은 HTTP 호출 수를 1~200으로 허용한다. [코드 어댑터](../../src/main/kotlin/io/intenttrace/record/adapter/out/github/GitHubGitEvidenceClient.kt)의 스냅샷 하나에도 커밋과 트리의 두 호출이 필요하다. [history](../../src/main/kotlin/io/intenttrace/record/application/ChangeIntentHistoryService.kt)는 재개할 때 새 캐시를 만들고 미완료 근거를 처음부터 처리한다.

따라서 호출 제한이 1인 상태에서 과거 커밋의 근거를 확인하면 커밋 조회 후 트리 조회 전에 중단된다. 같은 조건과 상태로 재개하면 다시 커밋 조회부터 시작해 같은 근거와 커서에 머무른다. 기한이 한 근거를 처리하기에도 부족한 상황에서도 같은 문제가 생길 수 있다. 이 결론은 코드 경로에 근거하며 이번 검토에서 전체 history 재개 요청을 실행한 결과는 아니다.

기본값 40회가 모든 조회를 막는다는 의미는 아니다. 설정과 응답 속도에 따라 최소 작업 하나도 완료할 수 없는 경우를 현재의 일반적인 이어 읽기 안내와 구분해야 한다.

완료 기준:

- 최소 확인 단위를 완료할 수 없는 호출 수 설정을 거부하거나, 원격 확인 단계 안에서도 진행을 이어갈 수 있게 한다.
- 재개 후에도 근거 순서가 진행하지 못한 경우 원인과 설정 조정·재시도 방법을 안내한다. 클라이언트는 같은 커서를 무조건 자동 반복하지 않는다.
- 미확인 근거의 위치와 권한 검사를 유지한다. 요청 사이에 객체나 중간 결과를 보관하는 방식을 선택한다면 보관 범위·용량·TTL을 ADR에 먼저 정한다.
- 낮은 호출 제한에서의 재개, 한 근거보다 짧은 기한, 정상적인 이어 읽기만 필요한 만큼 확인한다.

## 검토 범위

제품 코드·의존성·테스트·DB는 변경하지 않았다. 합성 세션과 임시 Zed 대역, 생성기 사본과 임시 의존성으로 두 현상을 확인한 뒤 임시 파일을 정리했다. 실제 사용자 세션, 실제 Zed 앱, GitHub 사용자·게시 요청은 사용하지 않았다. 전체 회귀 테스트는 재실행하지 않고 검토 문서와 인수인계 링크만 추가했다.
