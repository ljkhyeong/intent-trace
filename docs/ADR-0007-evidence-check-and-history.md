# ADR-0007: 코드 증거 확인과 이전 기록 조회를 분리한다

## 상태

채택. 2026-09-05 기능 개선 요청에 따라 구현한다.

## 결정

- 코드 근거는 `BASE`·`TARGET`을 구분한다. BASE 근거에는 전체 base 커밋이 필요하다. 이름 변경은 반대쪽 근거의 `relatedPath`로 연결한다.
- 클라이언트 실행 결과는 `CLIENT_REPORTED` 또는 `LOCAL_RUNNER_REPORTED`로 출처를 표시한다. 두 값 모두 서버가 테스트 실행을 증명한 것은 아니다.
- 서버 코드 확인은 인증된 사용자의 GitHub token으로 커밋·트리·blob을 읽어 수행한다. 사용자 token에 `Contents: read`가 필요하며 게시용 installation token 범위를 넓히지 않는다.
- 코드 확인 결과는 요청 시 계산해 기록 ID·버전·커밋·스냅샷·확인 시각과 함께 반환한다. 공개 본문이나 기존 해시를 갱신하지 않으며 코드 원문을 DB에 저장하지 않는다.
- 스냅샷은 `git -c core.quotePath=true ls-tree -r --full-tree`의 UTF-8 출력에 SHA-256을 적용한다. 파일 mode·객체 type·객체 ID·탭·Git의 경로 인용 규칙·LF를 고정한다. 서버는 트리의 leaf를 Git 경로 순서로 정렬해 같은 출력을 만든다.
- 일부만 반환한 GitHub tree, 없는 파일, 범위 밖 줄과 제한을 넘는 blob은 확인 성공으로 처리하지 않는다. 줄 해시는 원래 줄 끝 바이트를 유지한다.
- 현재 커밋과 다른 기록은 별도 탐색 결과로 반환한다. 조상 여부와 파일 blob이 같다고 서버가 확인한 경우만 파일 동일로 표시한다. 관련 후보에는 원본 커밋을 표시하고 검증 결과를 현재 검증으로 승격하지 않는다.
- 로컬 실행 도구는 검증 명령을 실제 실행하고 출력 해시·종료 코드·시각을 수집한다. 실행 전후 Git 상태가 대상 커밋과 다르면 현재 커밋 검증으로 내보내지 않는다. 출력은 메모리에서 해시만 계산하고 파일로 저장하지 않는다.

## 영향

GitHub 읽기 권한·장애·호출 제한이 코드 확인에 영향을 준다. 기존 기록 조회는 별도 서버 확인을 강제하지 않는다. 코드 확인 성공도 로컬 테스트 실행이나 작성자 의도의 사실성을 증명하지 않는다.

## 이름 변경과 줄 이동 확장

저장소 공개 후보를 제한된 페이지로 조회하고 각 후보의 원본 커밋을 현재 커밋과 비교한다. 같은 blob의 고유한 경로 이동만 이름 변경으로, 원본 해시가 맞는 코드 조각의 고유한 전체 줄 일치만 줄 연결로 인정한다. 중복 조각과 수정된 코드를 유사도로 연결하지 않는다. 원본·현재 줄 범위를 함께 반환하며 이전 테스트를 현재 검증으로 취급하지 않는다. 후보 페이지가 비어 보이더라도 다음 커서가 있으면 조회를 이어갈 수 있다. 코드 원문은 조회 요청 동안만 메모리에 둔다.

## 0.10.0 조회 실패 경계

인증 요청마다 생성하는 `GitHubUserSession`에 저장소별 권한 결과를 보관한다. 장기 세션 저장소에는 이 객체를 넣지 않으며 새 요청에서 권한 회수를 다시 확인한다. 원격 권한 조회 예외는 캐시하지 않는다.

과거 기록 조회는 최대 8개 스냅샷·8개 blob·40개 조상 비교를 각각 LRU 캐시에 보관한다. 후보 간 같은 객체와 지원 불가 결과를 재사용하고 요청이 끝나면 버린다. blob 한 개는 기존 2 MiB 제한을 유지한다. 실제 지연 시간 개선 폭은 측정하지 않았다.

크기 제한·일부 트리·지원하지 않는 객체는 별도 예외 타입으로 변환해 후보 실패로 반환한다. HTTP 인증·권한·호출 제한과 일반 장애는 이 타입으로 바꾸지 않는다. 실패한 기록은 ID로 다시 조회할 수 있게 하여 후보 페이지 진행과 재시도를 분리한다. 확인 불가 기록을 일치 결과로 표시하지 않는다.

## 0.12.0 조회 중단과 재개

- history 호출마다 `EvidenceReadBudget`을 새로 만들고 기본 30초·GitHub 코드 HTTP 호출 40회로 제한한다. `intent-trace.history.time-limit`은 양수·최대 40초, `max-remote-calls`는 0.12.1부터 7~200으로 설정한다. 사용자 인증은 기존 요청 경계에서 수행한다. 이 제한은 모든 HTTP 요청의 응답 시간을 보장하는 서비스 SLA가 아니다.
- 실제 커밋·트리·blob·조상 관계 HTTP 호출 직전에 횟수를 차감한다. 캐시 적중은 차감하지 않는다. 원격 호출은 기존 10초와 남은 기한 중 짧은 값으로 요청·본문 읽기를 제한한다. JDK HTTP 클라이언트는 redirect를 따르지 않으며 기존 인증·호출 제한·지표 처리를 유지한다.
- 근거 처리 전후에 기한과 실행 스레드의 interrupt를 확인한다. 기한·호출 수·전달된 취소는 `stopReason=TIME_LIMIT|CALL_LIMIT|CANCELLED`, `complete=false`와 함께 반환한다. 브라우저 탭을 닫거나 MCP 요청을 취소했을 때 모든 전송 경로가 서버 스레드를 즉시 중단한다는 보장은 없다. 전달되지 않은 취소는 서버 기한으로 제한한다.
- 중단 응답의 `nextCursor`는 조회 조건 해시, 현재 기록의 생성 시각·ID, 아직 반환하지 않은 근거 순서, 남은 후보 수와 다음 페이지 유무를 담는다. 코드·세션 원문을 저장하지 않는다. 같은 조회 조건의 `cursor`에 그대로 넣으며 클라이언트가 해석하지 않는다.
- 공개 본문과 근거 순서는 고정되어 있다. 재개 시 저장소 권한·공개 상태·기록 생성 시각·근거 범위를 다시 확인하고 아직 반환하지 않은 근거부터 읽는다. 이미 반환한 근거를 다시 붙이거나 남은 후보를 건너뛰지 않는다.
- 0.12.0부터 이미 처리한 근거 결과는 같은 후보의 후속 근거에서 지원 불가가 발생해도 반환한다. `failures`는 그 후보의 나머지 근거를 확인하지 못했다는 뜻이다. 실패 ID 재조회는 후보 전체를 다시 확인하므로 기존 같은 후보 결과를 교체한다. 중단 커서 재개는 반환되지 않은 근거를 추가한다. 인증·권한·호출 제한과 일반 장애는 계속 전체 요청 실패로 처리한다.

## 0.12.1 진행하지 못하는 조회 처리

- 한 근거의 원본·현재 커밋과 트리 4회, 조상 비교 1회, 두 blob 2회를 합해 빈 캐시에서 최대 7회가 필요하다. 서버 정책은 7회 미만 설정을 시작 시 거부한다. 기본 40회는 유지한다. 원격 확인 단계가 추가되면 최소 호출 수와 검증도 함께 갱신한다.
- 현재 요청의 첫 후보·첫 미완료 근거를 끝내기 전에 기한 또는 호출 수에 도달하면 `resumeBlocked=true`다. 최초 조회와 재개 모두 적용하며, `stopReason`으로 원인을 유지한다. 관련 없는 근거를 정상 처리해 다음 근거로 넘어간 경우에는 결과가 비어 있어도 false다. 취소는 false이며 사용자 요청 없이 자동 재개하지 않는다.
- 재개 위치를 유지하되 자동 반복하지 않고 설정·GitHub 응답 지연 확인을 안내한다. 설정 조정이나 응답 회복 뒤 같은 커서로 다시 조회할 수 있다. 서버의 `time-limit`을 최대 40초 안에서 조정하거나 GitHub 연결 상태를 확인한다. 40초에도 한 근거를 완료하지 못하면 요청을 계속 반복하지 않는다.
- 근거 중간의 응답을 요청 사이에 보관하지 않는다. 기존 요청 전용 캐시와 매 요청의 권한 확인을 유지한다. 따라서 최소 호출 수가 충족돼도 시간 내 처리가 항상 보장되지는 않는다.
