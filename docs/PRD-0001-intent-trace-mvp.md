# PRD-0001: IntentTrace MVP

## 상태

초기 MVP 완료. GitHub 게시는 `PRD-0002`, 팀 사용자·저장소 접근과 승인 세션은 `PRD-0003`에서 정의한다.

## 문제

AI가 코드를 빠르게 만들수록 작성자와 팀원은 결과를 이해하는 데 더 많은 시간을 씁니다. 일반적인 diff와 Git blame은 누가 무엇을 바꿨는지는 보여주지만, 어떤 요청과 판단으로 바뀌었고 실제로 무엇을 검증했는지는 보여주지 않습니다.

## 목표

개발자가 한 코드 변경을 다시 볼 때 다음 질문에 짧고 검증 가능한 답을 얻습니다.

1. 어떤 사용자 요청 때문에 생겼는가?
2. 어떤 판단을 적용했으며 그 판단의 출처는 무엇인가?
3. 정확히 어느 커밋·파일·줄에 연결되는가?
4. 어떤 명령을 실제로 실행했고 결과는 무엇인가?
5. 무엇을 검증하지 않았는가?

개인 이해를 첫 번째 가치로 두고, 작성자가 확인한 같은 기록을 팀 리뷰와 인수인계에 재사용합니다.

## 사용자 흐름

1. AI가 코드 변경과 필요한 검증을 마친다.
2. AI가 원문 대화 대신 구조화된 요약으로 비공개 초안을 만든다.
3. 작성자가 요청, 판단 출처, 코드 근거, 검증, 미검증 항목을 확인한다.
4. 작성자 확인 시 기록을 전체 커밋과 스냅샷에 묶는다.
5. 공개 요청 시 스냅샷을 다시 확인하고 팀 조회를 허용한다.
6. 내용이 바뀌면 기존 공개 기록을 수정하지 않고 새 기록으로 대체한다.

## 범위

### 포함

- 로컬 서버와 GitHub 인증 사용자 실행
- REST와 MCP를 통한 기록 생성·수명주기·조회
- 커밋·코드 줄·검증 해시 근거
- Markdown 공유 문서
- Codex 플러그인 스킬과 안내 훅

### 제외

- 대화 원문 수집
- 숨은 추론 저장
- IntelliJ 플러그인
- GitHub 조직 정책과 별도의 자체 계정 관리
- AI가 목적을 사실처럼 자동 확정하는 기능

## 성공 기준

- 같은 요청 ID의 재시도가 기록을 중복 생성하지 않는다.
- 작성자 확인 전에는 공개할 수 없다.
- 스냅샷이 바뀌면 확인과 공개가 실패한다.
- 파일과 줄로 공개 기록을 찾을 수 있다.
- 실행하지 않은 검증과 추론된 목적이 UI·응답에서 구분된다.
- REST와 MCP가 같은 생성 입력 제약과 전체 Git 커밋 ID 형식을 적용한다.

## 후속 단계

GitHub PR 게시 계약은 `PRD-0002`, GitHub 사용자·저장소 권한과 웹 승인·token 갱신 계약은 `PRD-0003`으로 확장했습니다. 다음으로 IntelliJ 라인 조회, 보존 정책과 감사 로그를 연결합니다.
