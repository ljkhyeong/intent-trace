# 설계·검토 문서 작성

짧고 구체적인 한국어로 쓰고 API 이름·경로·설정 키·enum은 원문을 유지한다. 확인한 사실, 제안, 미확인을 구분하고 확인하지 않은 동작을 단정하지 않는다. 표현은 [문구 검토](../../../docs/reviews/2026-09-05-wording-review.md)의 `그대로 유지할 표현`을 따른다. 문서만 바꿨다면 서버·IDE 테스트 없이 링크와 형식만 확인한다.

## PRD·ADR

- 번호는 같은 종류의 최대 번호에 1을 더한다. `ADR-0007`·`PRD-0004`는 이미 두 문서가 같은 번호를 쓰므로 새 문서에 기존 번호를 다시 쓰지 않는다.
- 파일은 `docs/<PRD|ADR>-<네 자리 번호>-<영문-주제>.md`, 제목은 `# <PRD|ADR>-<번호>: <한국어 제목>`이다.
- PRD는 `문제`·`목표`·`사용자 흐름`·`계약` 또는 `범위`·`불변식`·`성공 기준`·`제외` 중 필요한 절을 쓴다. 입력·응답 필드와 오류는 REST·MCP 이름 그대로 적는다.
- ADR은 `상태`(`채택` 등)·`배경`·`결정`·`영향`·`대안`을 쓴다. 권한·비밀값·트랜잭션·외부 호출 경계를 결정에 적는다.
- 기존 계약을 넓히면 새 문서 대신 해당 문서 끝에 `## <버전> <주제>` 절을 추가한다(`ADR-0009`·`ADR-0010` 방식).
- 새 문서는 [개발 스킬](../../../skills/intent-trace-flows/SKILL.md)의 기능별 문서 표와 README `문서` 목록에 연결한다.

## 검토 문서

`docs/reviews/YYYY-MM-DD-<주제>-review.md`에 쓴다. 제목 아래 머리말은 다음과 같다.

```markdown
검토일: YYYY-MM-DD

기준 커밋: `<전체 커밋 ID>`

상태: <제안 범위. 반영 후에는 반영 버전과 검증 기록 링크>
```

- 첫 절은 `우선순위` 표(`순서`·`우선순위`·`항목`·`확인 방법`)다. P1은 다음 작업에서 우선 처리할 항목, P2는 그다음 확장이나 사용량에 따라 추진할 항목이다.
- 항목마다 근거 링크(`../../src/main/kotlin/...kt#L30`처럼 기준 커밋의 줄), 재현 방법과 결과, 최소 변경, 완료 기준을 쓴다. 재현하지 않고 코드로만 확인한 내용은 그렇게 적는다.
- 반영한 뒤에는 본문 수치·줄 번호를 검토 당시 기준으로 두고 머리말 상태만 갱신한다.

## 구현·검증 기록

`docs/reviews/YYYY-MM-DD-v<버전>-verification.md`에 쓴다.

- 머리말은 `검증일`과 `범위`(반영한 검토 문서 링크)다.
- `## 구현` 표(`항목`·`반영한 내용`), `## 실행한 검증` 표(`검증`·`결과`)와 실행 환경을 쓴다. 실행하지 않은 확인(실제 IDE·GitHub 게시·원격 CI)은 따로 밝힌다.
- HANDOFF `다음 작업 후보`에 검토 문서와 검증 기록을 잇는 문단을 추가한다.
