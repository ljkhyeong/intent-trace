# 작업 마무리와 검증 기록

시작 커밋: `$ARGUMENTS` — 비어 있으면 작업 시작 때 기록한 커밋을 쓴다. 기록이 없으면 아래 이력에서 이번 작업 직전 커밋을 고르고 근거를 밝힌다.

- 최근 커밋:
!`git log --oneline -8`
- 브랜치와 작업 파일:
!`git status --short --branch`

## 1. 구현 커밋

1. `python3 scripts/feedback.py finish --base <시작 커밋>`을 실행하고 출력된 `review.diff`를 끝까지 읽는다. 누락·계층 의존·불필요한 변경을 고쳤다면 지역 검사와 `finish`를 다시 실행한다.
2. 변경 범위의 검증이 현재 코드로 실행됐는지 확인한다. 없으면 [개발 스킬](../../../skills/intent-trace-flows/SKILL.md)의 변경별 검증을 실행한다. 같은 코드·환경·범위의 성공 결과는 재사용하고 재사용이라고 적는다.
3. 이번 작업 파일만 지정해 stage한다. 작업 전부터 있던 미추적 파일은 stage하지 않는다.
4. `<종류>: <한국어 요약>`으로 커밋한다. 종류는 이력과 같이 `feat`·`fix`·`refactor`·`perf`·`docs`·`build`·`ci`·`test` 중에서 고른다.

## 2. HANDOFF 기록

구현 커밋 뒤 HANDOFF.md를 고친다. 이전 날짜 절은 수정하지 않는다. 파일 끝에 다음 형식의 절을 추가하고, 제목은 구현 커밋 요약에 맞춘다.

```markdown
## YYYY-MM-DD <작업 제목>

- 시작 리비전은 `<시작>`, 구현 커밋은 `<구현>`이다. <바꾼 동작과 유지한 동작>. <측정한 코드량 변화가 있으면 그 값>.
- <실행 명령>에서 <테스트 수>가 통과했다. <확인한 동작>. 결과 시각은 YYYY-MM-DD HH:MM KST다. <로그를 남겼다면 개인 경로가 없는 위치>. <새 테스트 추가 여부>.
- <적용한 지역·전체 diff 검사>. <바뀌지 않아 반복하지 않은 검증>. <하지 않은 작업: 실제 IDE 설치·GitHub 게시·원격 푸시·배포>. <보존한 미추적 파일>.
```

`최근 검증` 표에서 해당 대상 행의 `검증한 코드`를 구현 커밋으로, 결과를 `[요약](#앵커)`로 바꾼다. 새 대상이면 행을 추가하고 표 위 기준 날짜를 갱신한다. 앵커는 제목을 소문자로 바꾸고 `·`·괄호 같은 문장 부호를 지운 뒤 공백을 `-`로 바꾼다. 예: `## 2026-09-12 DB 시간 변환을 표준 API로 정리` → `#2026-09-12-db-시간-변환을-표준-api로-정리`.

- 이번 실행, 이전 결과 재사용, 미실행을 구분한다. 다른 커밋·스냅샷의 결과를 현재 검증으로 쓰지 않는다.
- 테스트 수와 결과 시각은 Gradle 출력이나 `python3 scripts/test-summary.py <실행한 대상>`에서 확인한 값만 쓴다. 측정하지 않은 성능·절감은 쓰지 않는다.
- 원문 출력·대화·토큰·개인 절대 경로를 넣지 않는다.
- `다음 작업 후보`·`현재 제한`은 내용이 바뀐 경우에만 고친다.

## 3. 기록 커밋

1. 훅의 통과 문맥이 없으면 `python3 scripts/feedback.py files HANDOFF.md`를 실행한다.
2. `docs: <작업 주제> 검증 결과 기록`으로 커밋한다.
3. 원격 푸시·PR·배포는 사용자가 요청한 경우에만 한다.
